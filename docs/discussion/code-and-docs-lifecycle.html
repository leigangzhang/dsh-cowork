02 · 统一模型

五种状态，五种动作

状态从机械事实推导，不从目录名推导；每项资产只占一个状态，并绑定一个 owner 阶段。状态是当前判断，不是永久身份。

current

当前实现

产品正在调用，代表当前语义；测试跟随当前行为契约。

动作随版本正常演进；不需要退役清单。
例m12 E2E · 当前行为测试
compat

兼容层

产品仍在调用，但不是目标实现；例如 legacy 字段、视图和 thread 别名。

动作绑定移除版本；下一次 minor / major；读写一起处理。
例legacy fields · thread alias
dev-only

维护者面

阶段驱动、探针或维护者工具，非验收面；只在仍有守卫价值时保留。

动作写复审触发条件；不能证明价值就退役。
例m2/m3 driver · probe · fixture
historical

历史证据

阶段交接/结果、归档记录与决策历史；只读保留。

动作只追加指针或事实更正；不回填交付证据。
例M6–M12 RESULT · archived
dead

死资产

无产品调用，也没有独立守卫价值；包括为其续命的测试。

动作代码 + 续命测试 + 断言一起删；先迁移价值。

判定纪律
  • 产品调用指真实路径；只在测试中出现，不能升级为 current。
  • 替代者先成立，才能把资产判为 dead；否则先留在 dev-only。
  • compat 必须绑定版本；下一次 minor / major，读写同批移除。
  • 静态 grep 只是线索；删除前先 deprecated 一个周期，并跑全量检查。
  • historical 不是垃圾桶；过期代码不能靠改标签变成历史证据。
  • 一个资产一个状态；跨状态就拆开登记，不共享同一行。
状态台账触发条件

状态是当前判断；触发条件变化时重新判定，不沿用旧标签。

08 · 节奏与版本

在收口和发版时做，而不是想起时做

把退役绑在已有节拍上，避免一次大扫除。巡检是读、比对、记录，不是自动删除；结论必须回到阶段 RESULT。

版本策略
每个里程碑收口一次 prune 巡检，建议 ≤30 分钟；结论写进 RESULT。
READ · GREP · CHECK · RECORD
每次 minor 发布前移除已到期的 compat / dev-only 资产；如 0.3.0。
REMOVE DUE ASSETS
patch保留兼容，不做退役；只修当前行为。
KEEP COMPAT
major才允许语义重写；历史与证据链仍然保留。
SEMANTIC REWRITE ONLY
可观察的触发条件0.3.0 发布 · legacy 读路径移除 · 发布线关闭 · 预算逼近上限
未处理项不消失：转 KNOWN_ISSUES，写清归属阶段与重估触发条件。

10 · 可选的自动化

先做只读报告，不把它变成门禁

静态“零引用”有误报；硬门禁会诱导改测试绕过。报告只是巡检输入，去留仍由人判断。

tools/lifecycle-report.mjs · 预期输出（示意）
$ node tools/lifecycle-report.mjs
NO_PRODUCT_REF<N>
TEST_ONLY_REF<N>
DEV_ONLY_ROUTE<N>
EXPIRED_KI_ASSET<N>
# read-only · no writes · no gate
报告→ 人工复核→ 台账→ 删除 / 归档 / 保留
先看NO_PRODUCT_REF：真正没有产品引用的候选
再看TEST_ONLY_REF：只在测试里续命的代码
最后EXPIRED_KI_ASSET：绑定了已过期 KI 的资产
报告不回答替代者是否成立 · 触发条件是否到期 · 删除要同步什么 · 保留还是删除
运行频率：每个里程碑收口或每次 minor 前；不进入 CI，也不阻塞合并。
A5 是可选交付：先能列出清单，再谈是否进门禁；没有报告也能执行前四个阶段。
为什么不直接当门禁

零引用不是死亡证明

  • 误报来源：动态导入、字符串工具名、测试夹具，都可能让静态扫描看不见调用。
  • 激励错误：一旦变硬门禁，最省力的变绿方式就是删测试或改夹具。
  • 先积累：规则稳定两个版本后再评估是否升级；期间只读。
  • 不自动删：报告给候选，删除仍需人工确认和同步清单。
升级前先满足：
□ 规则稳定两个版本
□ 误报率可接受，且有豁免机制
□ 报告仍不自动删除，只给候选
三个误报场景
动态 import：路径拼在字符串里
工具名写在数组或配置里
测试夹具仍在调用旧实现
人工复核看什么
① 替代者是否已经存在？
② 触发条件是否可观察、已到期？
③ 同步清单是否完整？
顺序不能反：先报告、后判断；先积累、后门禁。
POSITIONStage 4 · A5；可选交付，不阻塞前三阶段。
SCOPE只读；不写文件，不自动删除。
UPGRADE规则稳定两个版本后，再评估门禁。

12 · 边界与风险

边界比清单更重要

边界不是谨慎，而是防止“治理”变成另一种破坏。最容易出事的地方，是误删动态引用，以及台账漂移成第二份文档。

四条不做
  • 不自动删代码删除必须人工确认；报告只给候选。
  • 不删历史证据gitignored 证据按保留策略处理，不随代码清理。
  • 不改写已推送历史退役通过新提交完成，不重写证据链。
  • 不为“清零”改测试不把测试改成夹具了事，也不删掉有效断言。
  • 不把归档当删除归档只适合证据 / 记录；仍有 dev 路由的代码不能靠归档消失。
边界的目的让删除可审计、可回滚；不是让删除变慢。
删除前：grep + deprecated 一个发布周期 + 全量检查。
风险与对策
风险对策
误删动态引用 / 字符串工具名先标 deprecated 一个发布周期；删除前 grep，跑全量检查；报告只当线索。
台账变成第二份文档而漂移台账只放状态与指针；细节归 docs/testing.md / KNOWN_ISSUES；收口时校验一致性。
自动报告误报，诱导绕过先只读，两个稳定版本后再评估门禁；始终人工确认。
把退役做成范围外顺手改删除只覆盖当前任务；不做无关重命名或重排，diff 只包含退役面。
版本窗口错配compat 只在下一次 minor / major 移除；0.3.0 一次性，不跨 patch 拆兼容层。
删除后不跑检查删除后复跑 owning checks；source-budget 断言随删除一起更新。
把历史文档回填成现状历史只追加指针或事实更正，不回填交付证据。
策略再次失效重估条件：出现多团队并行贡献，或单文件 / 文档预算再次逼近上限。
真正的护栏：替代者先成立、版本绑定、同批同步、检查仍绿。
STEP 01grep 产品 / 测试 / 字符串引用
STEP 02deprecated 一个发布周期
STEP 03跑全量 / owning checks
STEP 04更新台账、RESULT、KI
