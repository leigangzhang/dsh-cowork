02 · 五类处理方式

把每样内容分成五类，再按类别处理

分类看实际情况，不看文件放在哪个目录。每样内容只归一类，并写清由哪个阶段负责。提案原文给这五类用了英文名，本页统一换成中文。

现在使用

产品正在使用

代表现在的做法；测试跟着当前行为走。

处理随版本正常修改；不需要删除计划。
例子m12 完整流程测试 · 当前行为测试
为旧版本保留

旧版本还能用

产品还在用，但这是旧做法；例如旧字段、旧页面数据和旧工具名。

处理写清在哪个版本删除；下一次小版本或大版本；读和写一起处理。

判断时注意
  • 产品使用指真实路径；只在测试里出现，不能算现在使用。
  • 先有替代方案，才能判“没有用了”；否则先保留。
  • “为旧版本保留”必须写清删除版本；下一次小版本或大版本，读和写一起处理。
  • 搜索引用只是线索；删除前先标记一版，再跑全部检查。
  • 历史记录不是放旧代码的地方；过期代码不能靠改分类变成历史记录。
  • 一样内容只归一类；跨类就拆开登记，不共用一行。
类别清单删除条件

类别是当前判断；条件变化时重新判断，不沿用旧标签。

三个容易判错的地方

暂时不用 → 不等于历史记录
有替代方案 → 不等于已经换好
拿不准：不删，写清以后什么时候再看。

05 · 代码怎么处理

不同类别，删除范围不同

删除不只是一个函数。它还会影响测试、开发入口、文件大小检查和文档。按类别决定范围，按版本时间执行。

没有用了第一批候选

先把有用的检查移走，再删

产品不用，也没有保留下来做检查的价值：删除代码，同时删除只为它存在的测试；有用的检查先移到新的测试。

  • renderMemoryEntry / formatMasterMessage
  • 数据存储模块的四个旧评审方法；测试覆盖先迁到新的评审请求模型
  • 删除前先标记一版，再搜索引用并跑全部检查
完成：搜索不到产品使用，检查已迁移，所有检查仍通过
一起改：测试 · 单文件大小检查 · 删除前搜索

0.3.0 一次处理完

  • 测试 + 开发入口 /e2e/m2|m3 + 相关测试
  • 单文件大小检查 + 文档引用

旧版本保留还在使用

同一个小版本或大版本，读写一起删

不允许只删读或只删写；删除前先把说明和问题记录处理完。

  • README 说明这次改动会让旧用法失效 + 关闭问题记录

06 · 测试和工具

测试和工具怎么处理

测试不能让没用的代码一直留着；工具也不是永远都要保留。两样都要有明确的使用范围和停止使用的时间。

测试只保留三类
01
现在行为的检查证明当前产品会怎样工作，包括边界和出错情况。
02
旧版本兼容的检查只保护还在使用的旧做法；旧做法删除时一起删。
03
项目规则的检查文件大小、文档分类、工作流程和自检。
没用的代码，不为它保留测试：只为它存在的测试一起删；有独立价值的检查先迁移，再删。
完整流程测试：用来验收，不是普通单元测试；流程换了就换测试，不能用单元测试代替。
删测试前先问
① 它还在保护旧版本吗？
② 它是不是只为没用的代码存在？
迁移顺序
找到检查 → 移到新的测试 → 删除旧测试

现在说明

08 · 什么时候做检查

什么时候做检查

把清理放在阶段结束和小版本发布前，不靠临时想起来。检查是读清单、搜索引用、跑检查、写结论，不会自动删除。

版本怎么安排
每个阶段结束做一次清理检查，建议 30 分钟以内；结论写进阶段结果。
读 · 搜索 · 检查 · 记录
每次小版本发布前删除已经到了删除时间的旧版本内容和开发维护内容，比如 0.3.0。
删除到期内容
小修复版本只修当前问题，不删除兼容内容。
保留兼容内容
大版本才允许改产品做法；历史记录仍然保留。
只在大版本改做法
可以观察的删除条件0.3.0 发布 · 旧读取路径删除 · 这一版发布结束 · 文件大小接近上限
没处理完的内容：转问题记录，写清负责阶段和什么时候重新看。
30 分钟检查
1
读清单找删除条件已经满足、没有负责人、替代方案没落实的条目。
2
搜索引用在产品代码、测试、入口和字符串里搜索；搜索结果只是线索。
3
跑对应检查文件大小检查、发布文件检查、npm run check、npm test；按改动范围选择。
4
判断类别条件满足就进入删除；不满足就保留，并写清什么时候再看。
5
写结论更新清单和阶段结果；没处理完的转问题记录，并写清哪个阶段做。
开始前：打开清单、阶段结果、问题记录三处，先确认这次要处理哪些条件。
检查不是删除。每次删除仍要人确认，并按“一起改”的清单执行。
产出 01清单：类别、负责人、删除条件更新
产出 02阶段结果：本次检查结论和未处理项
产出 03问题记录：负责阶段和什么时候重新看
09 · 执行步骤

分四步执行

不要一开始就删。先写清分类、替代方案和删除时要改的地方，再按版本安排处理；第一步不改任何代码。

01

写规则和清单

在 docs/testing.md 增加一节，说明五类和检查时间；建清单，登记第一批可以删除的内容。

  • 类别、负责人、替代方案、删除条件、一起改的内容
  • 只写规则和清单，不改产品代码
完成：验收 1；npm run check 通过。
风险：清单写成第二份文档
验收 1文档和计划
02

删除第一批没用的内容

处理 renderMemoryEntry、formatMasterMessage 和数据存储模块的四个旧评审方法。

  • 先把有价值的测试覆盖移走，再删只为它存在的测试
  • 同步修改测试和文件大小检查
完成：验收 2；代码和检查一起删除。
风险：只删代码，不删测试
验收 2源代码

10 · 可选的自动检查

先做只查看的检查结果，不把它变成必须通过的检查

只靠搜索判断有没有人使用，会看错。把检查设成必须通过，又会让人删测试来通过。所以先只生成候选清单，是否删除仍由人判断。

tools/lifecycle-report.mjs · 预期输出（示意）
$ node tools/lifecycle-report.mjs
没有产品调用<N>
只在测试里调用<N>
只在开发时使用的入口<N>
和过期问题记录有关<N>
# 只查看 · 不写入 · 不强制
检查结果→ 人工确认→ 清单→ 删除 / 归档 / 保留
先看没有产品调用：真正可能没人用的内容
再看只在测试里调用：只为测试存在的内容
最后和过期问题记录有关：问题结束了但内容还在
检查结果不回答替代方案是否存在 · 删除条件是否到了 · 删除时要改什么 · 到底删不删
什么时候运行：每个阶段结束或每次小版本发布前；不放进自动检查，也不阻止代码合并。
验收 5 是可选项：先能列出清单，再谈是否加入必须通过的检查；没有它也能做前三个步骤。
为什么不直接作为必须通过的检查

搜不到使用，不等于可以删除

  • 会看错：按字符串加载的代码、写在字符串里的工具名、测试辅助代码，都可能让搜索看不到使用。
  • 会让人改测试：一旦变成必须通过，最省事的做法就是删测试或改测试辅助代码。
  • 先积累：规则稳定两个版本后，再决定是否升级为强制检查；期间只查看。
  • 不自动删：检查结果只给候选，删除仍要人确认和同步修改。
升级前先满足：
□ 规则稳定两个版本
□ 误报可以接受，并且有例外处理办法
□ 仍不自动删除，只给候选
三个会看错的情况
按字符串加载：路径写在字符串里
工具名写在数组或配置里
测试辅助代码仍在调用旧实现
人工确认看什么
① 替代方案已经有了吗？
② 删除条件能观察、已经到了吗？
③ 要一起改的内容列全了吗？
顺序：先有检查结果，再判断；先使用一段时间，再决定是否强制。
位置第 4 步 · 验收 5；可选项，不影响前三个步骤。
范围只查看；不写文件，不自动删除。
升级规则稳定两个版本后，再决定是否强制。

12 · 限制和风险

不能做的事和常见风险

写清限制，是为了删错时能查、能恢复，也避免把还在用的内容当成历史记录。

五条不做
  • 不自动删代码删除要人确认；检查结果只给候选。
  • 不删历史记录被忽略的历史证据按保留规则处理，不随代码一起清理。
  • 不改写已经发布的历史清理通过新提交完成，不重写以前的记录。
  • 不为“清零”改测试不把测试改成辅助代码了事，也不删有效检查。
  • 不把归档当删除归档只适合历史记录；还有开发入口的代码不能只靠归档。
写清限制的用途让删除可以检查、可以恢复；不是为了拖慢处理。
删除前：搜索引用 + 标记一版 + 跑全部检查。
风险和处理办法
风险处理办法
误删仍被使用的内容 / 写在字符串里的工具名先标记一版；删除前搜索引用，跑全部检查；检查结果只当线索。
清单变成第二份文档清单只放类别和位置；细节留在测试说明 / 问题记录；阶段结束时核对。
自动检查误报，诱导绕过先只查看，两个稳定版本后再决定是否强制；始终人工确认。
把清理做成顺手改删除只覆盖当前任务；不做无关重命名或调整顺序；改动只包含清理范围。
版本时间错配旧版本内容只在下一次小版本 / 大版本删除；0.3.0 一次处理，不跨小修复版本拆。
删除后不跑检查删除后重跑对应检查；文件大小检查随删除一起更新。
把历史文档改成现在说明历史只补充链接或更正事实，不补写交付证据。
规则再次不够用重新判断：出现多个团队同时修改，或文件 / 文档大小再次接近上限。
删除前确认：替代方案已经存在、版本已经写清、要改的地方同批处理、检查仍然通过。

下一步怎么做
