dsh-cowork · 会话架构 · 讨论稿

主会话、主题
与评审的重新分工

交接和评审从对话里搬到插件；主题是具体任务的唯一会话入口；评审按请求触发；并行工作放进隔离目录。三条原则，重排整个流程。

01 · 约束

先立三条原则，后面每个设计都拿它量

现在的实现同时违反这三条。它们不是三个独立问题，而是同一个结构问题的三种表现：交接和评审这些流程消息占用了对话的位置。

01
MASTER
上下文 ∝ 用户交互量
≠ 工程量
现在∝ 主题数 × 事件数：每个交接 / 评审结论都会唤醒并留下全文
机制流程交给插件 · 事件合并 · 固定长度的状态摘要
02
TOPIC
上下文 ∝ 主题寿命
≠ 任务数量
现在每个任务新建会话，重复加载项目规则与记忆，重复熟悉代码
机制一个主题一个会话 · 进行中 / 空闲 / 已解决 · 已解决不自动接消息
03
REVIEW
成本 ∝ 变更与风险
≠ 每次交接
现在每次进入待评审就新建会话读仓库，文档改动也一样

共同原因　交接、评审、状态同步都走主会话的对话消息，于是主会话的负担跟工作量一起增长。

两个真实 case 产生 2 个主题会话 + 2 个评审会话；加上早期 1 个没有评审的会话，索引里已有 3 个主题会话、2 个评审会话。它们全部留在列表里，每条投递也留在主会话的对话里。

PAIN 01

PAIN 02

03 · 分工

master 只做决定，流程交给插件

状态同步不该由主会话来做；只要用对话同步，每个事件都会进一次会话。边界要写进工具面，不能只写在提示词里。

master

决定与对话
  • 项目级入口；主题会话是具体任务的入口
  • 定优先级、拆分主题
  • 例外决定：合并、发布、阻塞、跨主题冲突
  • 对用户汇报
对话内容 = 用户消息 + 分配卡 + 决定卡。细节只在被问时读状态摘要。

插件

流程与状态
  • 维护主题三态（进行中、空闲、已解决）和待评审、阻塞标记
  • 接收评审请求，做确定性检查
  • 创建和回收 reviewer、隔离目录
  • 合并事件、固定长度状态消息、分配、记忆
这些现在是 master 的提示词在推；改成插件后主会话不再承担流程。

主题会话

会话入口与执行
  • 一个主题一个会话，内部可以有多个执行单元
  • 跑验证、交证据（file:line、命令）
  • 发起评审请求，不等 master 转交
  • 写主题摘要和证据级记忆
同一主题内的任务共用这段对话；已解决后不再自动接消息。

reviewer

风险检查
  • 只按评审请求启动
  • 只看请求范围与证据
  • 每次新建，用完回收；轮次 ≤2–3
  • 给出具体问题和修改要求
独立性靠独立会话；只读目前靠约定（KI-15）。
master 不做：创建或转发评审、读代码、跑测试、逐条安排评审、读全文交接、维护每个主题的细节。
边界要写进工具面：master 现在仍带 fs/bash，只靠提示词约束；KI-10 记录过它调用 dev_* 宿主管理工具。
04 · 主题模型

主题不是标题，是决策面 + 交付面

状态只有三种：进行中、空闲、已解决。待评审和阻塞是标记，不是状态。已解决不自动接收消息，用户手动打开可以继续。

一个主题 = 一组会互相影响的决定 + 一组共享的交付物 / 文件面。
  • 1两件事会否认或推翻对方的决策？
  • 2会改同一批文件、接口或数据？
  • 3一方完成，会让另一方的验收标准失效？
任一为「是」→ 同主题；全为「否」→ 不同主题。
主题内多任务（todo、多个执行单元）是常态；跨主题只共享项目记忆，不共享代码上下文。

05 · 路由

路由三层：越往后越贵，低置信不自动建

目标不是一次就分配对，而是错了一次点击能改。纠正产生的数据反过来成为下一次分配的依据。

LAYER 1
会话局部性

最近提到的主题、上次分配的目标、用户刚打开的主题 —— 默认续接

成本 ≈ 0
LAYER 2
结构化匹配

输入里的路径、模块、符号、产品术语 ↔ 主题的范围、负责文件、别名

确定 · 可解释
LAYER 3
模型兜底

只剩 1–2 个候选时，一次小模型调用；关闭推理（thinking: False）；只给候选范围（≤2k 字），输出选择与置信度；短超时，超时按低置信

最贵 · 有界
输出与兜底
  • 复用：把原话发给该主题，并带一句话说明
  • 新建：插件自动起名，带 1–3 句背景说明
  • 低置信：不弹选择，模型在候选里选一个；选错可一键改投
  • 纠正：一键改到别的主题，写进别名，参与下次匹配
用户改投→ 别名学习→ 下次匹配↺
现在为什么不准
  • 只看字面词：标题命中 ×3 + 交接摘要命中 ×2，阈值 4、领先 1 分（router.ts:57）
  • 中文按两字一组匹配，「资源」「页面」这类词容易误命中；准确度依赖 master 起标题
  • 「继续」「再改一下」和标题没有共同词 → 直接新建
  • 已解决不参与自动分配是对的，但当前没有手动重开的入口
一次意图的走查
输入「把详情页的同类推荐做成卡片，放右栏」
L1 局部性上一条消息在「热门榜单页」主题 → 续接候选
L2 实体「详情页 / 同类推荐」命中「详情页信息架构」的 scope 与 ownedPaths
决策复用「详情页信息架构」· L3 不触发 · 置信度高
06 · 评审

评审按风险分级，按评审请求触发

评审单位是一次「评审请求」定义的改动范围，不是一个执行单元。请求由主题会话显式发起，插件做确定性检查，reviewer 只看这次改动的差异；master 不在创建和转发的链路里。

风险分级
L0
讨论 / 调研 / 状态

不建评审会话；标准是结论带证据（file:line、命令、实验）

≈0
L1
文档 / 配置 / 单文件小改且已验证

机器检查全绿即可，不建评审会话；用户手动 review 过记为一次评审事件

低
L2
公共接口 / 数据结构 / 迁移 / 安全 / 并发、跨模块、多分支合并、改动超阈值

独立评审；一次请求一次，评累计差异；轮次 ≤2–3

中
L3
破坏性迁移 / 发布 / 外部副作用

人类批准；reviewer 不能替代这个决定

高
不评仓库，只评请求：起点提交到终点提交的差异 + 验证证据 + 风险清单；不重新探索仓库、不重跑全套测试。
评审请求的预设字段
范围起点提交 → 终点提交，绑定分支
位置隔离目录的绝对路径（worktree）
改动changedPaths + 这次要做到什么
证据跑过的命令、退出码、结果
历史上一轮的问题与修复情况
显式请求→ 插件检查→ 新建 reviewer→ 用完回收
预设字段不是强制表单；真实会话里由模型决定保留哪些、补充哪些。检查项：范围内有改动、工作目录干净、声明的检查真的跑过。任一不满足就退回主题，不建 reviewer。每次请求新建会话，不复用；上一轮记录随请求带过去。
并行场景：子代理 / AgentTeams / 隔离目录
各自隔离

每个执行单元一个目录、一个分支；主题是集成分支的负责人。

评哪个差异

互不影响的分支分别评；会互相影响的，先合到集成分支，再评合并结果。

冲突不入评审

冲突由发起合并的人解决，解决后重新请求评审；reviewer 不合并、不解决冲突。

只留一个评审负责人

AgentTeams 的内部 review 算自检；cowork reviewer 做最终评审，不要两层都全量评。

子代理默认继承父会话的工作目录和上下文：它可以做日常检查，但 L2 的最终评审要用独立会话，或用与主题无关的干净上下文。评审记录写回主题：范围、轮次、结论、评审者。

08 · 目标链路

新的事件流：master 只在决策点被唤醒

流程由插件推进；交接正文落文件，主会话只收合并后的摘要；评审按请求创建，用完回收。

GAIN 01
事件合并

不再每个交接 / 评审结论唤醒 master；攒到用户下次说话或需要决定时投一条

GAIN 02
正文留文件

交接与评审的完整记录在 .dsh-cowork/；投递只有元数据与摘要

GAIN 03
评审不常驻

L0/L1 不建会话；L2+ 每次新建、用完回收；子代理只做日常检查

09 · 成本结构

同样的工作，成本挂在哪里

把「随什么增长」换对：master 跟交互走，主题跟主题寿命走，评审跟风险走。

维度现在目标机制
master 对话内容随主题 / 事件线性增长：全文投递 + 一次返回全部状态与用户交互同阶流程交给插件 · 事件合并 · 固定长度摘要
主题会话冷启动每个新主题重新加载；已解决被手动续接时重新加载同一主题内复用；续接由用户明确选择三态管理 · 已解决不自动接消息
评审成本每次进入待评审就新建会话，读仓库跑命令随 L0–L3 与改动规模按请求 · 只看改动差异 · 用完回收
可见会话2 个 case → 6 个常驻（本机索引）1 个：master；主题会话在面板主题会话不进左侧栏 · 评审会话回收
记忆写入所有事件都可能经 master 进入对话主题写证据、master 整理来源字段 · 验收点整理
会话数来自 .dsh-cowork/index.json 实测；master 轮数为代码路径推断（分配 / 交接 / 评审结论各一次投递），未单独埋点计数。

10 · 落地

如果只做三件事

按收益排序；每件都有可验证的验收信号，不靠「感觉变好了」。

01
流程交给插件 + 合并消息 + 固定长度状态摘要

交接 / 评审由插件推进；master 只收决策消息；状态查询改为固定长度的摘要。

验收：master 每个 case 的流程轮数 ≤1；不再接收全文交接。
02
主题三态 + 局部性分配 + 一键纠正

进行中 / 空闲 / 已解决；已解决不自动接消息，用户可手动重开；分配先看当前主题。

验收：同一主题的连续任务复用会话；已解决续接由用户选择；每次纠正可解释。
03
按评审请求 + 隔离目录 + 单一评审负责人

L0–L3；每次请求新建 reviewer；评隔离目录里的分支差异；AgentTeams 自检与 cowork 终评只选一个。

验收：文档改动不产生评审会话；评审会话数 = L2+ 请求数。
本轮已定
已定master 保留合并 / 发布决定权；机械合并由插件做，人工审批入口留给 master。
已定不单独设讨论型主题类；讨论型主题不提交评审请求，就不会触发评审或合并。
已定主题会话不在左侧栏；优先宿主 / 插件过滤，退路用归档隐藏；位置放右侧栏 CoWork tab，默认显示普通会话。
已定低置信不弹选择；模型在候选里选一个，选错可一键改投。
这些决定会进入实施；具体操作方式在执行前再定。
最大不确定：宿主 / 插件是否有办法按会话过滤左侧栏。优先用过滤；没有过滤时退回归档隐藏，再验证隐藏后用 openSession 打开能否正常继续对话。
